# KP14 moments crash, 2026-08-26

All 11 KP14 jobs from the 2026-08-26 run crashed. BGN and GS21 ran clean. Diagnosed from
`outslurm/kp14_*_crash.pkl`.

**Verdict: a single bad commit (`005a63e`, 2026-07-02) desynchronized `sdf_compute_kp14.py`
from the `arr_tuple` that `generate_panel.py` writes to disk. Not an economics problem, not
a memory problem, not a cluster problem.**

## Symptom

All 11 crash pickles are byte-for-byte the same failure:

```
ScriptError: utils/calculate_moments.py failed with return code 1

File "utils_kp14/sdf_compute_kp14.py", line 95, in sdf_compute
    K, book, op_cashflow, x, z, eps, uj, chi, rate, high, Et_G, EtA, alph,
    Et_z_alph, price, ret, eret, lambda_f = arr_tuple
ValueError: not enough values to unpack (expected 18, got 16)
```

Panel generation **succeeded** — every `kp14_N_panel.pkl` is on disk (51.8 MB each,
written 08:06–08:07) and the crashes are at 08:10–08:12. The log shows the arrays loading
fine, sparse formats and all:

```
  [0] K: sparse (sparsity=99.3%)
  [4] uj: sparse (sparsity=49.9%)
  [5] chi: sparse (sparsity=99.3%)
Loaded 16 arrays: N=1000, T=720 (format v2)
```

The failure is the first executable statement of `sdf_compute`, before any arithmetic. Every
job died the same way in seconds, which is why all 11 crashed rather than some subset.

## Root cause

There are **two different KP14 `arr_tuple`s**, and `sdf_compute_kp14.py` was asking for the
wrong one.

| Stage | File | Arrays |
|---|---|---|
| built | `utils_kp14/panel_functions_kp14.py:205` | **18** — includes `book`, `op_cashflow` |
| saved | `utils/generate_panel.py:177-181` | **16** — strips `book`, `op_cashflow` for KP14 |
| loaded | `utils/calculate_moments.py:187` | **16** — reads back what was saved |
| consumed | `utils_kp14/sdf_compute_kp14.py:95` | asked for **18** ← the bug |

`generate_panel.py` strips those two arrays deliberately — they are needed to build the
panel (`bm`, `roe`, `agr`, the `book == 0` return screen) and not to compute the moments:

```python
# Strip book and op_cashflow from kp14 arr_tuple (only needed for panel creation)
if model_name == 'kp14':
    K, book, op_cashflow, x, z, ... = arr_tuple
    arr_tuple = K, x, z, ...
    del book, op_cashflow
```

## Who broke it, and when

```
ada933a  2026-01-25  Kerry Back      "Fix arr_tuple mismatch in sdf_compute modules"
f8a46a4  2026-01-26  Kerry Back      adds the strip; shrinks the kp14 unpack 18 -> 16
eae09bb  2026-06-30  sjpsjpsjp       adds the zero-capital screen: keep = K_slice.sum(axis=0) > 0
005a63e  2026-07-02  alexanderober   "changed to keep book instead of K, adjusted arr_tuple"
```

`005a63e` made two edits:

```diff
-    K, x, z, eps, uj, chi, rate, high, Et_G, EtA, alph, Et_z_alph, price, ret, eret, lambda_f = arr_tuple
+    K, book, op_cashflow, x, z, eps, uj, chi, rate, high, Et_G, EtA, alph, Et_z_alph, price, ret, eret, lambda_f = arr_tuple
...
-        keep = K_slice.sum(axis=0) > 0                          # risky firms with capital
+        keep = book[t,:] > 0                          # risky firms with capital
```

The screen change is the intent; the unpack change is collateral, needed only to get `book`
into scope. But it "adjusted arr_tuple" toward the **pre-strip 18-array tuple**, which never
reaches this function. `ada933a` had fixed this exact class of bug six months earlier, and
`f8a46a4` had shrunk the unpack to 16 the next day — `005a63e` silently undid that half.

**The KP14 moments step has not run since 2026-07-02.**

### Why BGN and GS21 were unaffected

The strip is guarded by `if model_name == 'kp14'`, and `005a63e` touched only
`sdf_compute_kp14.py` (3 insertions, 4 deletions, one file). Neither of the other two models
has a saved-vs-expected discrepancy.

## Fix

The two screens are the **same test**, so `005a63e`'s screen change was a no-op that cost a
crash. In `panel_functions_kp14.py:144`:

```python
book = x/z*K.sum(axis = 0)
```

`x` and `z` come from `sim_gbm`, so both are strictly positive, and `K >= 0`. Therefore

```
book[t,:] > 0   <=>   K[:, t, :].sum(axis=0) > 0   <=>   K_slice.sum(axis=0) > 0
```

(the last step because `K[s,t,:] = 0` for every `s > t` — `chi` is built by `cumsum` along
axis 1 from a diagonal, so a project cannot exist before it arrives). `K_slice` is already
computed ~150 lines earlier in the same function, so the revert is free.

Applied to `utils_kp14/sdf_compute_kp14.py`: restore the 16-array unpack, restore
`keep = K_slice.sum(axis=0) > 0`, and leave a comment at both sites recording the contract —
this is the third time this file has drifted from it.

### The other direction is worse

Not stripping `book` would also compile, but `SPARSE_INDICES['kp14'] = {0:'K', 4:'uj', 5:'chi'}`
in `utils/generate_panel.py:194` is hardcoded to the **stripped** layout. Re-adding two
arrays shifts `uj` and `chi` to indices 6 and 7. The guard is

```python
if i in sparse_config and arr_np.ndim == 3:
```

so index 4 (now `z`, 2-D) falls through, and `uj` and `chi` — both TxTxN at 99.3% and 49.9%
sparsity — would be written **dense**, with no error raised. Tens of GB per panel, silently.

## Verification

Reproduced locally at N=30, T=60: built the arrays, applied the exact strip
`generate_panel.py` applies, then ran `sdf_compute` and `sdf_loop`.

```
saved n_arrays = 16
t=  5  sdf_ret=-3.377624e-01  max_sr= 1.456424e+00  nkeep= 11  screens_match=True
t= 20  sdf_ret= 2.250073e-02  max_sr= 2.121523e+00  nkeep= 21  screens_match=True
t= 40  sdf_ret=-1.473826e-01  max_sr= 2.307288e+00  nkeep= 22  screens_match=True
```

Also confirmed on that panel:

- `x > 0` and `z > 0` at every date (`x`, `z` are shape `(T+1, 1)` aggregate processes).
- `K[s, t, :]` is identically zero for all `s > t`, at all 61 dates — so the full-axis sum
  inside `book` equals the sliced sum inside `sdf_loop`.
- `(book[t,:] > 0)` and `(K_slice.sum(axis=0) > 0)` agree at **all 61 of 61** dates.
- The screen is load-bearing, not cosmetic: 3 to 30 of 30 firms are zero-capital depending
  on the date.

On the cluster `K` arrives as a `Sparse3D`; `get_col_slice_dense` returns a plain
`np.ndarray` (`utils/sparse_3d.py:151`), so `.sum(axis=0)` is valid on the production path
as well as the dense backwards-compat path.

## Caveat before trusting the output

This makes KP14 **run**; it does not make KP14's numbers trustworthy. Independent of this
crash, `integ_results.npz` returns exact zeros over the region where ~98% of firm-months
live (`quad(f, 0, 10)` against a CIR density with sd ~0.006), which makes the "true" `rp`
equal to `-PVGO/P` — wrong sign, sd ~173x too large. Resubmitting is worth it to confirm the
pipeline completes end to end, but hold the moments until the quadrature is fixed.

## Prophylactic worth considering

`utils/calculate_moments.py` prints `Loaded {len(arr_tuple)} arrays` and hands the tuple
straight to `sdf_compute`. Nothing validates the count against what the consuming module
expects, so a mismatch surfaces as a bare `ValueError` deep in a model file after the panel
step has already burned its wall-clock. Each `sdf_compute` declaring its expected length
(or `metadata['n_arrays']` being checked against it) would fail fast with a legible message.
Three separate commits have now hit this.
