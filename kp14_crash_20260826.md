# KP14 moments crash, 2026-08-26

All 11 KP14 jobs from the 2026-08-26 run crashed. BGN and GS21 ran clean. Diagnosed from
`outslurm/kp14_*_crash.pkl`.

**Verdict: a single bad commit (`005a63e`, 2026-07-02) desynchronized `sdf_compute_kp14.py`
from the `arr_tuple` that `generate_panel.py` writes to disk. Not an economics problem, not
a memory problem, not a cluster problem.**

A second, unrelated defect blocks the *numbers* rather than the run:
`integ_results.npz` is corrupted by a quadrature failure introduced on 2026-06-18, and its
solution files are on mixed parameters. That is diagnosed in the second half of this
document, from "Separate blocker" onward, and is not addressed by the fix here.

## Symptom

All 11 crash pickles are byte-for-byte the same failure:

```
ScriptError: utils/calculate_moments.py failed with return code 1

File "utils_kp14/sdf_compute_kp14.py", line 95, in sdf_compute
    K, book, op_cashflow, x, z, eps, uj, chi, rate, high, Et_G, EtA, alph,
    Et_z_alph, price, ret, eret, lambda_f = arr_tuple
ValueError: not enough values to unpack (expected 18, got 16)
```

Panel generation **succeeded** — every `kp14_N_panel.pkl` is on disk (51.8 MB each,
written 08:06–08:07) and the crashes are at 08:10–08:12. The log shows the arrays loading
fine, sparse formats and all:

```
  [0] K: sparse (sparsity=99.3%)
  [4] uj: sparse (sparsity=49.9%)
  [5] chi: sparse (sparsity=99.3%)
Loaded 16 arrays: N=1000, T=720 (format v2)
```

The failure is the first executable statement of `sdf_compute`, before any arithmetic. Every
job died the same way in seconds, which is why all 11 crashed rather than some subset.

## Root cause

There are **two different KP14 `arr_tuple`s**, and `sdf_compute_kp14.py` was asking for the
wrong one.

| Stage | File | Arrays |
|---|---|---|
| built | `utils_kp14/panel_functions_kp14.py:205` | **18** — includes `book`, `op_cashflow` |
| saved | `utils/generate_panel.py:177-181` | **16** — strips `book`, `op_cashflow` for KP14 |
| loaded | `utils/calculate_moments.py:187` | **16** — reads back what was saved |
| consumed | `utils_kp14/sdf_compute_kp14.py:95` | asked for **18** ← the bug |

`generate_panel.py` strips those two arrays deliberately — they are needed to build the
panel (`bm`, `roe`, `agr`, the `book == 0` return screen) and not to compute the moments:

```python
# Strip book and op_cashflow from kp14 arr_tuple (only needed for panel creation)
if model_name == 'kp14':
    K, book, op_cashflow, x, z, ... = arr_tuple
    arr_tuple = K, x, z, ...
    del book, op_cashflow
```

f8a46a4  2026-01-26  Kerry Back      adds the strip; shrinks the kp14 unpack 18 -> 16

`005a63e` made two edits:

```diff
-    K, x, z, eps, uj, chi, rate, high, Et_G, EtA, alph, Et_z_alph, price, ret, eret, lambda_f = arr_tuple
+    K, book, op_cashflow, x, z, eps, uj, chi, rate, high, Et_G, EtA, alph, Et_z_alph, price, ret, eret, lambda_f = arr_tuple

-        keep = K_slice.sum(axis=0) > 0                          # risky firms with capital
+        keep = book[t,:] > 0                          # risky firms with capital
```

The screen change is the intent; the unpack change is collateral, needed only to get `book`
into scope. But it "adjusted arr_tuple" toward the **pre-strip 18-array tuple**, which never
reaches this function. `ada933a` had fixed this exact class of bug six months earlier, and
`f8a46a4` had shrunk the unpack to 16 the next day — `005a63e` silently undid that half.

**The KP14 moments step has not run since 2026-07-02.**

### Why BGN and GS21 were unaffected

The strip is guarded by `if model_name == 'kp14'`, and `005a63e` touched only
`sdf_compute_kp14.py` (3 insertions, 4 deletions, one file). Neither of the other two models
has a saved-vs-expected discrepancy.

## Fix

The two screens are the **same test**, so `005a63e`'s screen change was a no-op that cost a
crash. In `panel_functions_kp14.py:144`:

```python
book = x/z*K.sum(axis = 0)
```

`x` and `z` come from `sim_gbm`, so both are strictly positive, and `K >= 0`. Therefore

```
book[t,:] > 0   <=>   K[:, t, :].sum(axis=0) > 0   <=>   K_slice.sum(axis=0) > 0
```

(the last step because `K[s,t,:] = 0` for every `s > t` — `chi` is built by `cumsum` along
axis 1 from a diagonal, so a project cannot exist before it arrives). `K_slice` is already
computed ~150 lines earlier in the same function, so the revert is free.

Applied to `utils_kp14/sdf_compute_kp14.py`: restore the 16-array unpack, restore
`keep = K_slice.sum(axis=0) > 0`, and leave a comment at both sites recording the contract —
this is the third time this file has drifted from it.

### The other direction is worse

Not stripping `book` would also compile, but `SPARSE_INDICES['kp14'] = {0:'K', 4:'uj', 5:'chi'}`
in `utils/generate_panel.py:194` is hardcoded to the **stripped** layout. Re-adding two
arrays shifts `uj` and `chi` to indices 6 and 7. The guard is

```python
if i in sparse_config and arr_np.ndim == 3:
```

so index 4 (now `z`, 2-D) falls through, and `uj` and `chi` — both TxTxN at 99.3% and 49.9%
sparsity — would be written **dense**, with no error raised. Tens of GB per panel, silently.

## Verification

Reproduced locally at N=30, T=60: built the arrays, applied the exact strip
`generate_panel.py` applies, then ran `sdf_compute` and `sdf_loop`.

```
saved n_arrays = 16
t=  5  sdf_ret=-3.377624e-01  max_sr= 1.456424e+00  nkeep= 11  screens_match=True
t= 20  sdf_ret= 2.250073e-02  max_sr= 2.121523e+00  nkeep= 21  screens_match=True
t= 40  sdf_ret=-1.473826e-01  max_sr= 2.307288e+00  nkeep= 22  screens_match=True
```

Also confirmed on that panel:

- `x > 0` and `z > 0` at every date (`x`, `z` are shape `(T+1, 1)` aggregate processes).
- `K[s, t, :]` is identically zero for all `s > t`, at all 61 dates — so the full-axis sum
  inside `book` equals the sliced sum inside `sdf_loop`.
- `(book[t,:] > 0)` and `(K_slice.sum(axis=0) > 0)` agree at **all 61 of 61** dates.
- The screen is load-bearing, not cosmetic: 3 to 30 of 30 firms are zero-capital depending
  on the date.

On the cluster `K` arrives as a `Sparse3D`; `get_col_slice_dense` returns a plain
`np.ndarray` (`utils/sparse_3d.py:151`), so `.sum(axis=0)` is valid on the production path
as well as the dense backwards-compat path.

## Separate blocker: the quadrature in `integ_results.npz`

This fix makes KP14 **run**. It does not make KP14's numbers trustworthy. A second,
independent defect corrupts every expected return and every SDF quantity the model produces.
Resubmitting is still worth it to confirm the pipeline completes end to end, but hold the
moments.

Reproduce everything below with `python diag_integ_kp14.py` (local, ~10 s, no cluster, no
panel data).

### The defect

`utils_kp14/integ_kp14.py:43` integrates a probability density of standard deviation
**0.006** over the interval **[0, 10]**:

```python
eps_max = 10
result = [quad(lambda ep: integrand(fun, ep), 0, eps_max, epsabs=1e-10, epsrel=1e-10, limit=500)[0]
          for fun in funcs]
```

Lines 34-36 define the CIR transition density of `eps`. Under current `config.py`,
`c = 8.2e-6`, `d = 3500`, `lam = 1.18e5 * eps`, giving mean `0.0288 + 0.971*eps` and
**sd ≈ 0.0057**. QUADPACK's initial 21-point Gauss-Kronrod rule on `[0, 10]` has no node
within ~17 sd of that spike, so the estimate *and its error estimate* are both ~0: `quad`
returns 0 and never subdivides. No warning, no exception.

The integral of the density alone must be 1.0 at every grid point. It is not:

```
    eps   density sd   mass on [0,10]     mass on narrow    E[A_mod] [0,10]   E[A_mod] narrow
   0.05     0.001438                0       1.0000000000                  0           873.621
   0.50     0.004053                0       1.0000000000                  0           4366.96
   0.95     0.005548       2.955e-131       1.0000000000       6.82963e-127           15948.2
   1.00     0.005690        5.649e-55       1.0000000000        1.30555e-50           18153.8
   2.00     0.008018        3.936e-79       1.0000000000        8.38619e-74            159094
```

### The damage

238 of 1000 grid points are exactly 0 in all 11 stored arrays. Worse, over the band the
simulation actually visits — `eps` is stationary with mean 1 and sd 0.0239, so ±4 sd is
`[0.9044, 1.0956]` — `Et_A_mod` is a **step function**: 0 or 1e-146…1e-12 below
`eps = 1.0490`, then ~2341 above. Truth at `eps = 1.0` is **18,108**.

`P(eps < 1.0490) = 98.0%`. So 98% of firm-months read exactly zero and the remaining 2%
read ~8x too small.

What that contaminates:

| | Source | Status |
|---|---|---|
| `PVGO`, `VAP`, `price` | `panel_functions_kp14.py:173-176` (uses `G_func.csv` directly) | clean |
| `rets` | `panel_functions_kp14.py:179` | clean |
| `EtA` / `term1`, `term3` | `panel_functions_kp14.py:187-188`, `:194` (closed form) | clean |
| `Et_G` / `term2` | `panel_functions_kp14.py:190-193` | **-> 0** |
| `term4` | `panel_functions_kp14.py:197` | **-> 0** |
| `erets` | `panel_functions_kp14.py:199` | **≈ -PVGO/price** |
| second moments | `sdf_compute_kp14.py:100`, `:212-226`, `:246-255` | **garbage** |
| `ER`, `cond_var`, `max_sr`, returned rp | `sdf_compute_kp14.py:262-263`, `:297-298`, `:305` | **garbage** |

`sdf_ret` (`:294`) multiplies clean realized returns by portfolio weights solved from the
contaminated `ER`, so it is dead too. `create_panel`
(`panel_functions_kp14.py:210-240`) exposes `ret`, not `eret`, so the panel handed to
FF/FM/DKKM survives — it is the true-SDF benchmark that is gone.

### It was working until 2026-06-18

Extracting the parent blob of `integ_results.npz` (the 2026-05-11 version, `sigma_eps = 0.2`):
**zero** exact zeros, monotone increasing, and accurate to **9.5e-5** against an independent
delta-method reference. `quad(f, 0, 10)` genuinely worked at `sigma_eps = 0.2` — sd ≈ 0.057
puts the nearest GK21 node ~1.7 sd from the mean, close enough that the initial rule sees
mass, gets a nonzero error estimate, and subdivides adaptively.

```
77c5ffc  2026-06-18 17:21:48  alexanderober  "Update config.py"
67a8914  2026-06-18 17:22:43  alexanderober  "Add files via upload"   <- 55 s later
```

`77c5ffc` cut `KP14_SIGMA_EPS` and `KP14_SIGMA_U` by 10x (and reverted `KP14_GAMMA_X`
`0.69*2 -> 0.69` and BGN's `SIGMA_Z` `0.4*2 -> 0.4`). `67a8914` regenerated `G_func.csv` and
`integ_results.npz`. The cut took the density sd from 0.057 to 0.0057, moving the nearest
quadrature node from ~1.7 sd to ~17 sd, where the pdf underflows. **A parameter change
silently converted a working integrator into a zero, and the corrupted output was committed
55 seconds later.**

No reason for the cut is recorded anywhere: both commit messages are GitHub web-UI defaults
with no body, there is no comment in the KP14 block of `config.py:238-262`, and no docstring
or doc references it. Dumping the values across all 48 `config.py` revisions shows what it
was, though — one person's parameter sweep, using a `<multiplier>*<original>` idiom to keep
the base value visible:

| date | author | `GAMMA_X` | `SIGMA_EPS` | `SIGMA_U` |
|---|---|---|---|---|
| Jan 23 – Apr 13 | Kerry Back | `0.69` | `0.2` | `1.5` |
| Apr 14 – Apr 27 | ober / sjp | `0.69` | `1.5*0.2` | `1.5` |
| May 11 – Jun 9 | ober | `0.69*2` | `0.2` | `1.5` |
| **Jun 18 (77c5ffc)** | ober | **`0.69`** | **`0.1*0.2`** | **`0.1*1.5`** |

So `77c5ffc` does two different things: reverts the May-11 doublings back to Kerry Back's
original January values (`GAMMA_X = 0.69` is intended, not a slip from deleting a `*2`), and
applies genuinely new 10x cuts to KP14's two idiosyncratic volatilities. `voc_diagnosis/README.md:52`
already flags these as "three undisclosed 10x idiosyncratic-volatility cuts."

### The solution files are also on mixed parameters

The regeneration in `67a8914` picked up the `sigma_eps` cut but **not** the `gamma_x` revert.
At `eps = 5` the quadrature happens to work (mass = 1), which makes this testable:

```
stored = 2.19047e6     gamma_x = 1.38 (pre-Jun-18) predicts 2.19029e6   ratio 1.000
                       gamma_x = 0.69 (config.py)  predicts 9.06006e6   ratio 0.242
```

Ratio 1.000 to four digits, at two separate grid points. `G_func.csv` is the same: it depends
on `gamma_x` through both `rho` and `util = C*A(eps,1)**(1/(1-alpha))` (`kp14_fd.py:78`), and
halving `gamma_x` moves `util` ~9x at `eps = 1` — but `G_func.csv` moved only 0.80x.

The May-11 solfiles *did* match `config.py`. The Jun-18 ones never have. The uncommitted
local `parameters_kp14.py` tracked one of the two edits in `77c5ffc` and not the other.

### Fix

Replace the fixed `[0, 10]` with the density's own quantile range:

```python
lam = 4*theta_eps*np.exp(-theta_eps*dt)*x0 / (sigma_eps**2*(1 - np.exp(-theta_eps*dt)))
lo = c * ncx2.ppf(1e-13, d, lam)
hi = c * ncx2.ppf(1 - 1e-13, d, lam)
result = [quad(lambda ep: integrand(fun, ep), lo, hi, epsabs=1e-12, epsrel=1e-12, limit=500)[0]
          for fun in funcs]
```

Validated over 91 grid points: worst `|mass - 1| = 3.5e-13`, worst deviation from an
independent delta-method reference `f(m) + f''(m)var/2` is **5.0e-9**. Because `sd/mean ≈ 5.7e-3`,
`E[f] ≈ f(mean)` — any method that resolves the spike lands in the same place, so the result
is not sensitive to the choice of limits.

Also replace the checks at `integ_kp14.py:45-50` with a mass check. Those three checks test
the integrand at `eps_max = 10` — the far tail, which is correctly ~0. They test the one end
that cannot fail. `assert abs(mass - 1) < 1e-8` at every grid point is the guard whose absence
let this ship.

### Producers now read `config.py` — DONE

`utils_kp14/integ_kp14.py` and `utils_kp14/kp14_fd.py` both used to do

```python
from parameters_kp14 import *
```

against a module that is not in the worktree and **never appears in any commit** — checked
every revision. Neither producer could be run as committed. That was the root cause of this
whole class of failure: as long as the producers read a file that is not in the repo, no
`config.py` change can be trusted to reach the solution files, which is exactly how the
`gamma_x` mismatch above happened.

Both now import explicitly from `config.py`, matching `sdf_compute_kp14.py:5-19`. The needed
names were enumerated by AST rather than by eye — 5 for `integ_kp14.py`, 10 for `kp14_fd.py`.
`kp14_fd.py` deliberately does **not** import `KP14_DT`: its `dt = 0.5` is the pseudo-time
step of the implicit FD iteration, not the model's time step, and there is a comment saying so.

Verified by running both, from a scratch CWD so the committed files were never at risk. At
`eps = 5` the quadrature happens to work (mass = 1), which makes the provenance testable:

```
fresh integ_kp14.py run = 9.06073e6   <- gamma_x=0.69 (config.py) predicts 9.06006e6
committed .npz          = 2.19047e6   <- gamma_x=1.38 (pre-Jun-18) predicts 2.19029e6
```

Fresh `G_up` at `eps ≈ 1` is **46x** the committed value, consistent with `rho` going from
0.1055 to 0.0158 plus the larger `A`. So both producers demonstrably track `config.py` now,
and the mixed-parameter staleness is confirmed by live runs rather than arithmetic.

Measured costs (both far cheaper than estimated): `integ_kp14.py` **~60 s** wall at
`n_jobs=7`; `kp14_fd.py` **~45 s**, converging at iteration ~3595 (`l2 < 1e-8`), nowhere near
its 1e6 cap. Full regeneration is under two minutes.

Still open on the producers: they read and write bare filenames in the CWD
(`integ_kp14.py:35`, `:87`, `kp14_fd.py:126`) rather than `KP14_solfiles/`, so today
regenerating means *cd into that directory and run them in the right order*. See below.

## Regenerating the solution files

Not one action — an ordered pipeline with a prerequisite.

```
config.py --> kp14_fd.py --> G_func.csv --+--> integ_kp14.py --> integ_results.npz --+
                                          |                                          |
                                          +------------------------------------------+--> sdf_compute_kp14.py     (import time)
                                                                                         panel_functions_kp14.py (import time)
```

`integ_kp14.py:35` reads `G_func.csv`, so **`G_func.csv` must be regenerated first, always**.
Run them out of order, or from the wrong directory, and you get new integrals computed against
the old `G` — the same defect diagnosed above, one level down. That is why the path fix is not
cosmetic: it is what makes regeneration reproducible instead of a manual ritual.

**Regenerating before the quadrature fix is worse than not regenerating.** You would get the
correct `gamma_x` with the same 238 zeros — a file that is still wrong but now *looks* freshly
generated, with a recent timestamp and a commit saying so. Right now the file's provenance is
visibly suspect, and that is the only protection in place.

### Three staleness modes, not one

| # | Failure | Instance |
|---|---|---|
| 1 | `config.py` moved, solfile did not | the `gamma_x = 1.38` bug — happened, undetected for two months |
| 2 | producer *code* moved, solfile did not | **will happen the moment the quadrature fix lands** |
| 3 | upstream solfile moved, downstream did not | `G_func.csv` regenerated without `integ_results.npz` |

Mode 2 is worth stating plainly: the quadrature fix *by itself* creates a stale-file
condition, because the committed `.npz` will no longer match the code that claims to produce
it. Whoever fixes the quadrature must regenerate in the same commit, or the repo is left in a
state that reads as fixed and is not.

### Mechanism: `KP14_solfiles/stamp.json`

One sidecar, written by the regeneration driver, verified at load. Per solution file:

- `sha256` of the file itself — so the stamp is provably *about these bytes*
- the config parameters used, as `name -> repr(value)` — `repr` because
  `KP14_SIGMA_EPS = 0.1*0.2` is `0.020000000000000004` and a rounded stamp would miss real edits
- `sha256` of the producer's source — catches mode 2
- `sha256` of upstream inputs (`integ_results.npz` records the `G_func.csv` it consumed) —
  catches mode 3

Verification yields a distinct message per mode rather than one vague "mismatch", which
matters when someone hits it on the cluster at 2am.

Sidecar rather than embedded because `G_func.csv` is read by `pd.read_csv` with positional
column use in two consumers — adding metadata columns risks them. The `.npz` could take extra
keys, but then the two files would be stamped by different mechanisms. One JSON is uniform,
greppable, and reviewable in a diff; its own drift is caught by the file hashes it contains.

The declared parameter list is **derived from each producer's own `from config import`
statement** by AST (`utils_kp14/solfile_spec.py`), not maintained by hand, so the spec cannot
drift from the code. Note that the derived parameters (`KP14_RHO`, `KP14_C`, `KP14_A_0..3`)
cover the transitive closure of the raw ones: `KP14_GAMMA_X` is imported by neither producer,
but it feeds `KP14_CONST -> KP14_A_*` and `KP14_RHO`, so stamping the derived values is what
catches the 2026-06-18 drift.

### Two phases, and why the split matters

The files are stale **now**, so the guard cannot simply be "verify and raise":

- **Hard-fail today** and KP14 stops running before the team has decided on the quadrature.
  That also blocks the one thing the crash fix bought — resubmitting to confirm the pipeline
  completes end to end.
- **Warn only, permanently** and the warning gets scrolled past. That is substantially how we
  got here.

**Phase 1 — landed, warn-only, no regeneration.** `utils/solfile_stamp.py` (model-agnostic)
plus `utils_kp14/solfile_spec.py`, called at module level in both consumers. It *cannot pass*,
because there is no `stamp.json` at all — and the absence of a stamp **is** the finding. Every
KP14 log now opens with:

```
==========================================================================
[SOLFILE STAMP] KP14: PROVENANCE UNVERIFIED
  G_func.csv               sha256:6669efae2997    60,236 B
  integ_results.npz        sha256:f46834aebd7a    90,820 B
  - no stamp.json in this directory, so these files cannot be checked
    against config.py or against their producers -- their provenance is
    unrecorded
  Known stale as of 2026-08-26, independently of the missing stamp:
    * integ_results.npz encodes KP14_GAMMA_X=1.38; config.py has 0.69.
    ...
==========================================================================
```

The short hashes are there so an old log identifies exactly which solfile vintage produced a
given number — the thing we could not do for the June run. The banner is deterministic (no
timestamps, no per-call-site text) and emitted once per process, so it is greppable on
`[SOLFILE STAMP] KP14`.

**Phase 2 — lands with the regeneration.** `stamp.json` appears, verification can pass, and
the call sites flip to `mode='error'`. The repo goes straight from *unstamped* to *stamped and
valid* and never passes through *stamped and failing* — which is the state that would invite a
permanent skip-the-check flag, and that flag would then be forever.

The useful inversion: the guard earns its keep **before** the fix precisely because it cannot
pass, and becomes an invariant **after**.

Phase 1 is tested against a fabricated stamp in a scratch copy — 8/8, covering a clean pass
(so Phase 2 is a flip, not a hope), all three staleness modes, bytes-changed-after-stamping, a
newly-declared parameter never stamped, a malformed `stamp.json` reported rather than raised,
and `mode='error'` raising. Confirmed non-blocking: panel and moments run unchanged with the
check in place.

`utils/solfile_stamp.py` is deliberately not KP14-specific. GS21 loads 12 solution files the
same way (`sdf_compute_gs21.py:27-40`) and has an independently documented economy mismatch
(`voc_diagnosis/README.md`). Same mechanism, different parameter list — a separate change.

### Sequence

1. Phase 1 banner — **done**; non-blocking, makes staleness visible while the team deliberates
2. team decides the quadrature fix
3. quadrature fix + path fix + mass check
4. regeneration driver + `stamp.json` + regenerate both files in order — **one commit**
5. flip both call sites to `mode='error'`
6. resubmit

Costs: quadrature fix + mass assert ~10 lines; path fix ~8 lines; regeneration driver ~70;
`stamp.json` writing folds into it; regeneration runtime ~105 s measured. Re-running panels and
moments on the cluster is the long pole — panels took ~1 minute in the crashed run, moments is
the expensive step.

One decision is genuinely the team's, and it belongs **before** step 4: whether
`KP14_GAMMA_X = 0.69` is right. The history says it is Kerry Back's original January value and
the `*2` was Alexander's own May-11 addition that he removed — but that is inference, not
something anyone stated. If it is wrong, `config.py` changes and everything downstream
regenerates again, so settling it after step 4 means doing step 4 twice.

## Prophylactic worth considering

`utils/calculate_moments.py` prints `Loaded {len(arr_tuple)} arrays` and hands the tuple
straight to `sdf_compute`. Nothing validates the count against what the consuming module
expects, so a mismatch surfaces as a bare `ValueError` deep in a model file after the panel
step has already burned its wall-clock. Each `sdf_compute` declaring its expected length
(or `metadata['n_arrays']` being checked against it) would fail fast with a legible message.
Three separate commits have now hit this.

The quadrature bug is the same failure mode one layer up: a silent contract violation between
a producer and a consumer, caught by nothing. Two cheap guards would have caught it at
write time rather than two months later —

- a mass check in `integ_kp14.py` (still to do — it belongs with the quadrature fix), and
- provenance stamping, which is now Phase 1 above. It catches the `gamma_x` mismatch, the
  regenerate-out-of-order hazard, and the code-changed-without-regenerating hazard, and it
  closes the gap that the uncommitted `parameters_kp14.py` opened.
